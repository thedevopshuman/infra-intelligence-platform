# Plugin compatibility report contract

**Status:** v1alpha1 local conformance evidence
**Machine contract:** `contracts/schemas/plugin-compatibility-report.schema.json`

`PluginCompatibilityReport` records what one concrete plugin artifact proved
against one host, SDK, protocol, container platform, and source revision. It is
generated by execution, not maintained as a marketing support claim. The first
matrix contains two profiles for the example Kubernetes observer:

- `offline-fixture` proves the public stdio input/output boundary in the signed,
  immutable, no-network, resource-bounded sandbox;
- `host-mediated-read` proves the same boundary with the separately immutable
  trusted relay, invocation-local socket, host-only credentials, and one
  policy/audit/broker-mediated provider read.

Every check is closed and machine-readable. A compatible profile contains only
`passed` checks and no error code; a failed check contains a stable error code.
Any failed check makes that profile and the overall report incompatible. The
repository runner removes stale output before execution and emits its positive
report only after every check passes, so a failed run cannot leave old evidence
looking current. The summary counts must exactly match the profile array, profile
names and check IDs must be unique, and both required profiles must be present
in reports emitted by the repository conformance runner.

Each row records its own manifest digest. The offline profile uses a separately
signed manifest with empty network and secret declarations; the mediated profile
uses the signed Kubernetes destination/credential upper bounds. Both select the
same immutable plugin image. A publisher signature covers the complete unsigned
manifest under `iip.plugin-signature/v2`, so one row's permission declaration
cannot be substituted into the other.

The report includes image and canonical manifest digests, but never publisher
private keys, capability tokens, endpoints, credential references, provider
responses, container IDs, tenant IDs, or actor IDs. `sourceDirty` is explicit:
a dirty local report remains useful for development but is not release
evidence. A customer support statement requires a clean source revision and the
customer's exact runtime architecture and integration interoperability gates.

This contract does not imply that one passing architecture supports another,
that fixture mediation proves a live credential issuer or provider, or that
read compatibility certifies the distinct proposal-only action mediation
profile. New plugin protocol versions and action-provider certification add
separate matrix rows or a new report contract when compatibility semantics
break; existing rows are never silently reinterpreted.
